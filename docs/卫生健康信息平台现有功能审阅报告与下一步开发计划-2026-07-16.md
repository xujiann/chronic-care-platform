# 卫生健康信息平台现有功能审阅报告与下一步开发计划

生成日期：2026-07-16

本报告基于当前 `chronic-care-platform` 工作区代码、`package.json` 脚本、`server.js` API、角色页面、`data/db.json` 演示数据、`release-artifact-manifest`、重点 readiness 脚本和现有文档进行审阅。当前工作区包含未提交的体检系统、院前急救系统、慢病信息化源清单、生产会话/安全边界等新增或调整内容，本报告将这些代码中已经存在的能力纳入现状，但仍按“演示/试运行准备”和“正式上线待现场签署”区分。

## 1. 总体结论

平台已经从早期慢病医防融合 MVP 扩展为一个覆盖居民服务、医疗机构协同、医保协同、公共卫生、妇幼、免疫、血液、体检、院前急救、质量安全、科研治理、数据治理和生产运维的综合卫生健康信息平台。

当前系统具备以下成熟基础：

- 统一入口：`login.html`、`index.html`、`platform.html`、`workbench.html` 和各角色页面已经形成多端入口。
- 角色权限：居民、医疗机构、卫生健康委、医保、医共体/区县、医生、护理、科研等角色均通过 API 和页面裁剪控制边界。
- 主数据与健康档案：以居民、家庭、`personIndex`、`personalRecords`、`diagnosticReports`、授权和审计为基础，支持居民健康档案、电子病历摘要、体检、影像、检查检验、慢病和服务记录归集。
- 平台总线：数据治理、接口映射、集成契约、幂等、签名、质量检查、血缘和发布证据链已形成可机读闭环。
- 发布证据：`release:manifest` 当前索引 68 个发布工件、4 个模板 README，覆盖 27 类能力；`package.json` 当前有 92 个脚本，其中 40 多个 readiness/report 类脚本。
- 数据快照：`data/db.json` 当前包含 215 个集合、约 1177 条演示/验收记录，已覆盖慢病、公卫、体检、急救、血液、医保、护理、科研、接口、生产运维等域。

总体状态判断：

- 功能形态：已具备较完整的演示级和试运行准备级功能体系。
- 工程形态：已形成 Node API + 静态页面 + JSON/SQLite/PostgreSQL 迁移证据 + readiness 脚本 + release/deploy 检查的混合架构。
- 上线形态：正式生产上线仍依赖真实身份源、短信/CA、HIS/EMR/LIS/PACS、医保核心、120 CTI/车辆设备、对象存储、监控/SIEM、灾备、等保/密评和现场签署。

## 3. 业务功能现状

### 3.1 居民端与家庭服务

已实现能力：

- 居民登录、手机号验证码演示、家庭成员裁剪。
- 健康档案、电子病历摘要、检查检验、影像云、体检报告、慢病随访、护理、陪诊、挂号、消息与待办。
- 授权共享、撤销、访问复核和服务评价/投诉入口。
- 居民端模块清单已经在 `citizen.js` 中标注实现状态、接口和生产边界。

下一步重点：

- 接入真实短信、实名认证、电子健康码/人口主索引。
- 补齐移动端 PWA 发布、消息送达回执、居民协议版本管理和撤权后的后端强拦截联动。
- 对居民端所有新增服务形成统一“服务订单中心”，减少护理、陪诊、挂号、体检、家医之间的重复订单模型。

- 慢病信息化源清单已覆盖 26 个来源、6 类来源分类、6 条能力轨道，`chronic:informatization-sources` 通过。

下一步重点：

### 3.3 区域体检系统

## 5. 主要问题与风险

### 5.1 功能面风险

- 功能覆盖已经很广，但部分模块仍是演示样例、模拟契约或本地闭环，容易被误读为生产完成。
- 居民端服务越来越多，护理、陪诊、挂号、体检、家医、急救之间存在“服务订单/消息/待办/评价”重复建模风险。
- 慢病、公卫、体检、急救、妇幼、免疫之间的重点人群和事件联动还需要统一规则中心。

### 5.2 集成面风险

- HIS/EMR/LIS/PACS、医保核心、疾控直报、120 CTI、电子证照、短信/CA 等关键接口均需现场联调。
- 部分接口已有签名和幂等演示，但尚未形成真实外部系统的回执样例、失败样例和压测结果。
- 数据字典、机构人员主数据和疾病/手术/药品/检查检验目录需要正式版本和责任人签署。

### 5.3 生产面风险

- 当前架构是混合应用：静态页面可预览，正式生产必须有 Node API、数据库、对象存储、监控、安全和灾备。
- PostgreSQL、对象存储、SIEM、备份、商密设备和生产环境变量尚需生产配置与演练。
- 正式上线必须保留 `external blocked` 和 `onsite blocked` 标识，不能用演示通过替代现场验收。

### 5.4 工程面风险

- `server.js` 已非常庞大，继续叠加模块会增加回归风险，建议逐步拆分领域服务和路由注册。
- readiness、release-report、deploy-check、manifest 四条证据链功能强，但新增模块时容易漏接其中一条。
- 工作区当前未提交改动较多，建议尽快分批提交，避免体检、急救、慢病源清单、生产安全边界互相覆盖。

## 6. 下一步开发计划

### P0：先收口当前在途功能并确保可发布

1. 提交前全量验证当前工作区
   - 范围：体检、院前急救、慢病信息化源清单、会话/安全边界、release/deploy 链路。
   - 验收：`npm.cmd run check`、`npm.cmd test`、`npm.cmd run deploy:check`、`npm.cmd run release:report` 全绿。

2. 建立“平台功能总览 API”
   - 范围：从 release manifest、package scripts、readiness 报告、数据集合生成平台能力总览。
   - 产出：`/api/platform/capability-map`、`platform.html` 能力总览卡片、报告导出。
   - 价值：让现有 68 个发布工件和 90+ 脚本可视化，避免后续开发迷路。

3. 统一服务订单与消息中心
   - 范围：护理、陪诊、挂号、体检、家医、急救、慢病随访的待办、通知、评价、投诉。
   - 产出：统一 `serviceOrders` 或兼容聚合层，不破坏现有模块集合。
   - 验收：居民端服务中心、机构端处置中心、卫健委监督中心均可查看跨模块状态。

4. 外部阻断项总台账
   - 范围：HIS/EMR/LIS/PACS、医保、疾控、120、证照、短信/CA、对象存储、SIEM、灾备。
   - 产出：统一 blocker API、责任人、现场窗口、证据包、签署状态和 release 警告。
   - 验收：`release:report` 可按 blocker 聚合，不再散落在各模块。

   - 完成 1 个急救中心、2 台车、1-2 家医院的演练链路。

3. 慢病医防融合现场联调
   - 出院随访触发、基层随访回写、药房取药、医保门慢门特、家医签约履约。
   - 建立慢病规则版本管理和质控闭环。

4. 公卫和免疫系统联调

## 7. 建议开发规则

后续开发继续遵循以下规则：

1. 平台优先：新功能必须接入现有角色、API、数据、发布证据和文档链路。
2. 最小权限：居民端、机构端、医保端、卫健委端、医共体端分别裁剪数据。
3. 主索引优先：所有居民相关数据必须可追溯到 `personIndex` 或稳定居民标识。
4. 外部接口诚实标注：未真实联调的接口必须保留 `onsite blocked` 或 `external blocked`。
5. 证据闭环：页面、API、数据、审计、readiness、测试、release/deploy 至少形成一条完整链。
6. 小步可验收：每次只做一个能运行、能测试、能在报告里看到的小切片。
7. 保护运行态数据：预览和探测优先使用临时 `DATA_DIR`，不要把噪声写入 `data/db.json`。
8. 文档即门禁：重要架构、边界、上线条件和现场阻断项必须有文档，并被静态测试或 readiness 检查覆盖。
