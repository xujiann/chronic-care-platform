# 数智医院标准平台 v0.19 任务与代码合并记录

## 一、合并结论

本次合并确定 `xujiann/chronic-care-platform` 的 `main` 分支为数智医院标准平台唯一代码主线，GitHub Pages 为公开演示入口。后续需求、代码、测试、报告和发布均在“数智医院标准平台建设”任务及该仓库中继续维护。

原“开发数智医院标准平台”任务不再作为并行开发主线。其独有的公共卫生事件协同能力已迁移到 v0.19；旧版 Next/Sites 包装层、重复的 v0.17 静态页面和私有演示部署不进入主线。

## 三、正确合并原则

1. 以功能更完整、已有 CI 和公开发布链路的 GitHub v0.18 为基线，不做双向文件覆盖。
2. 按能力迁移，不复制旧版框架外壳；避免把 v0.18 的生产运行时、评价工作台和试点工作台降级为 v0.17。
3. 公共卫生协同作为数智医院标准平台的专属工作台，与仓库已有的公共卫生专业系统并存：
   - 专业系统继续承担复杂直报、外部适配器、密钥、探测和生产韧性能力。
   - 数智医院工作台承担八通道概览、异常协同、状态推进、独立复核和投产边界展示。
4. 页面状态、后端状态、OpenAPI、JSON Schema 和测试使用同一组字段与正式路由。
5. 不把演示状态误标为生产可用。现场证据、真实业务回执、灾备演练和多方审批未完成时，`productionReady` 固定为 `false`。

## 四、v0.19 已迁移能力

### 4.1 公共卫生协同工作台

- 八类业务通道：传染病直报、免疫规划、妇幼健康、老年健康、慢病管理、公卫随访、健康教育、家庭医生。
- 三次连续活动及链路校验状态。
- P0/P1/P2 异常事件台账、责任人、时限、修订号和最新处置说明。
- “待核查 -> 处置中 -> 待复核 -> 已关闭”状态机。
- 创建、开始处置、提交复核、复核关闭的动作留痕。
- 连续性中断与恢复的浏览器演示。
- 现场证据和生产阻断清单。

### 4.2 后端运行与安全控制

- 卫健委角色访问控制。
- JSON 状态持久化和服务重启后的状态恢复。
- `expectedRevision` 乐观锁，拒绝并发覆盖。
- 提交人与关闭复核人不得相同。
- 拒绝 `secret`、`password`、`token`、`signature`、`nonce`、`credential`、证书、私钥和原始载荷字段。
- 每个创建和状态推进动作写入密封安全事件链。
- 无论演示数据是否全部通过，生产状态均保持关闭。

### 4.3 正式接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/digital-hospital/public-health/coordination` | 获取协同总览、通道、活动、事件、动作和生产边界 |
| `POST` | `/api/digital-hospital/public-health/incidents` | 登记最小化公共卫生协同事件 |
| `POST` | `/api/digital-hospital/public-health/incidents/{incidentId}/actions` | 按修订号推进事件并执行独立复核 |

上述接口已同步到 `digital-hospital-standard-platform/mock-api/openapi.v0.1.yaml`，公共卫生数据包已同步到 `package-schema.v0.1.json`。

3. 公共卫生 HTTP API 持久化测试。

5. 静态页面、OpenAPI、JSON Schema 接线测试。
6. Playwright 桌面端和移动端视觉检查。
7. GitHub Actions 全部通过。
8. GitHub Pages 发布后在线复核。

## 八、后续开发上下文

后续从 GitHub `main` 创建功能分支，继续使用现有 Node.js 后端和 `digital-hospital-standard-platform/` 前端，不再从旧 Sites 提交反向覆盖主线。

下一阶段优先事项：

1. 将协同事件与仓库已有公共卫生专业系统的事件编号、通道探测结果和证据摘要建立只读关联。
2. 增加医院范围过滤、SLA 超时升级、事件批量导出和处置统计。
3. 增加站点联调证据登记、双人签收和生产审批引用。
4. 现场接入真实系统时仅保存摘要、引用和审计信息，不保存原始敏感载荷。

旧任务在本次 v0.19 代码合并、CI 和 GitHub Pages 发布完成后归档；本记录作为两条任务开发上下文的长期交接材料。
