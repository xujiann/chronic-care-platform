# 公共卫生信息化下一步开发计划

生成日期：2026-07-08
适用范围：`public-health.html`、`GET /api/public-health/system`、公共卫生事件处置、数据交换、发布就绪和现场验收材料。

## 目标

公共卫生信息化系统已经完成标准矩阵、机构责任、事件队列、交换任务和发布证据的第一版。下一步开发要把系统从“标准展示和看板”推进到“可处置、可追踪、可验收”的工作台，优先围绕《全国公共卫生信息化建设标准与规范（试行）》要求的平战结合、医防融合、数据交换、安全审计和现场联调证据展开。

## 5 小时开发切片

| 时间 | 开发内容 | 交付物 | 验收清单 |
|---|---|---|---|
| 第 1 小时 | 梳理事件处置闭环和后续路线 | 本计划文档、建设报告补充 | 明确事件处置闭环、数据交换、现场联调、发布闸口 |
| 第 2 小时 | 建立公共卫生事件动作 API | `POST /api/public-health/events/:id/actions` | 支持复核、派发、闭环、备注、责任人、时限 |
| 第 3 小时 | 升级卫健委端公共卫生页面 | 风险队列操作按钮、动作历史、结果刷新 | 页面能直接触发事件处置并刷新系统摘要 |
| 第 4 小时 | 补齐 readiness、部署检查和发布报告证据 | `public-health:readiness`、`deploy:check`、`release:report` | 新增事件动作 API 和前端操作检查 |
| 第 5 小时 | 跑完整验证并整理下一阶段事项 | 测试结果、预览验证、剩余依赖 | `check`、专项测试、API 测试、部署/发布报告通过 |

## 两周路线

| 阶段 | 重点 | 产出 |
|---|---|---|
| 第 1 阶段：处置闭环 | 公共卫生事件动作、审计、责任人、时限、闭环证据 | 事件工作台、动作 API、审计链、测试 |
| 第 2 阶段：数据交换 | 疾控直报、实验室、免疫、妇幼、应急、安全审计六类交换任务细化 | 交换任务运行记录、失败补偿、回执状态 |
| 第 3 阶段：机构协同 | 疾控、基层、医院、监督、妇幼、卫健管理部门角色化视图 | 分角色任务摘要、机构责任清单、现场账号清单 |
| 第 4 阶段：现场验收 | 等保密评、国密、备份恢复、接口联调、签字材料归档 | 验收材料清单、阻塞项、证据台账 |

## 开发完成记录

完成日期：2026-07-09

本计划已开发到演示/验收发布包状态，具体完成如下：

1. 事件处置闭环：`POST /api/public-health/events/:id/actions` 支持复核、派发、闭环，写入 `publicHealthEvents.actionHistory` 和 `securityEvents`。
2. 数据交换：新增 `publicHealthExchangeRuns` 和 `POST /api/public-health/exchange-tasks/:id/runs`，覆盖六类交换任务的运行记录、回执状态、失败补偿和重放/人工复核。
3. 机构协同：新增 `publicHealthInstitutionTasks` 和 `POST /api/public-health/institution-tasks/:id/actions`，覆盖疾控、基层、卫健管理、监督、妇幼、医院和其他公卫机构。
4. 现场验收：新增 `publicHealthOnsiteAcceptances` 和 `POST /api/public-health/onsite-acceptances/:id/actions`，覆盖接口联调、等保密评、备份恢复、应急演练、账号确认和发布材料。
5. 前端工作台：`public-health.html` 已增加交换运行、机构协同、现场验收面板，`public-health.js` 支持记录回执、完成协同和记录签署。
6. 发布证据：`public-health:readiness`、`deploy:check`、`release:report`、`release:manifest`、静态测试和 API 测试均已纳入新增能力。
7. 继续开发：新增 `publicHealthCutoverBlockers` 和 `POST /api/public-health/cutover-blockers/:id/actions`，把正式接口、密钥、等保密评、备份演练和账号授权拆成可跟踪、可记录整改证据、可审计的上线阻塞项；`public-health.html` 新增上线阻塞面板，`public-health:readiness` 新增 `cutover:blockers` 和 `cutover:open-boundary` 检查。
8. 继续开发：新增 `publicHealthCutoverReadiness`、`GET /api/public-health/cutover-readiness`、`renderCutoverReadiness`、`cutover:readiness-board` 和 `publicHealth:cutoverReadiness`，把 P0/P1 开放阻塞、证据记录、red/amber 升级、现场窗口、提醒渠道和责任动作汇总成上线准备度 gate；当前 gate 保持 `site-evidence-required`，待现场证据全部关闭后才可变为 `production-ready`。
9. 继续开发：新增 `publicHealthCutoverEvidencePackets`、`GET /api/public-health/cutover-evidence-packets`、`POST /api/public-health/cutover-evidence-packets/:id/actions`、`renderCutoverEvidencePackets`、`cutover:evidence-packets` 和 `publicHealth:cutoverEvidencePackets`，把 6 个上线阻塞项拆成 20 项现场材料签收记录；每次登记材料都会写入 `public-health-cutover-evidence-packet-action` 审计，并同步刷新上线准备度证据摘要。
10. 持续开发：新增 `publicHealthLaunchApprovals`、`GET /api/public-health/launch-gate`、`POST /api/public-health/launch-gate/actions`、`renderLaunchGate`、`launch:gate` 和 `publicHealth:launchGate`，把标准矩阵、事件闭环、交换回执、机构交接、现场签字、证据包核验、阻塞项关闭和六方审批合成 production-ready gate；在现场材料未齐时继续显示 `site-evidence-required`，材料和审批全部通过后才允许转为 `production-ready`。
11. 持续开发：新增 `publicHealthSiteEvidenceBridge`、`GET /api/public-health/site-evidence-bridge`、`POST /api/public-health/site-evidence-bridge/actions`、`renderSiteEvidenceBridge`、`buildStaticSiteEvidenceBridge`、`site-evidence:bridge` 和 `publicHealth:siteEvidenceBridge`，把 `siteLaunchEvidence` 的 verified 现场材料映射到公共卫生上线证据包、现场验收项和上线 gate；桥接只抵扣证据，不自动关闭 P0/P1 阻塞项，避免把演示材料误判为真实生产 ready。

12. 持续开发：新增 `publicHealthCutoverDrills`、`GET /api/public-health/cutover-drills`、`POST /api/public-health/cutover-drills/:id/actions`、`renderCutoverDrills`、`buildStaticCutoverDrillBoard`、`data-public-health-cutover-drill`、`cutover:drill-board` 和 `publicHealth:cutoverDrills`，把接口切换彩排、应急指挥桌面演练、安全合规复测、备份回退演练和上线 go/no-go 会议纳入统一台账。演练记录只作为上线前复测证据和阻塞定位依据，不会自动关闭 P0/P1 阻塞项，也不会绕过现场材料桥接、证据包签收和多方 launch gate 审批。
13. 持续开发：新增 `publicHealthProductionHandoffs`、`GET /api/public-health/production-handoffs`、`POST /api/public-health/production-handoffs/:id/actions`、`renderProductionHandoffs`、`buildPublicHealthProductionHandoffBoard`、`buildStaticProductionHandoffBoard`、`data-public-health-production-handoff`、`production:handoffs` 和 `publicHealth:productionHandoffs`，把接口移交、应急指挥移交、安全合规移交、运维回退移交、七类机构账号移交和发布归档移交纳入 production handoff gate。所有移交包必须完成签收并归档 release artifacts 后，`launch-production-handoffs` 才能通过；默认状态仍保持 `site-evidence-required`，避免用演示材料替代真实现场签收。

发布边界：本计划完成的是可运行演示/验收包；正式生产上线仍以现场真实接口、密钥、等保密评、国密设备、备份恢复演练和签字材料到位为准。
14. 持续开发：新增 `publicHealthGoLiveObservations`、`GET /api/public-health/go-live-observations`、`POST /api/public-health/go-live-observations/:id/actions`、`renderGoLiveObservations`、`buildPublicHealthGoLiveObservationBoard`、`buildStaticGoLiveObservationBoard`、`data-public-health-go-live-observation`、`go-live:observation-plan` 和 `publicHealth:goLiveObservations`，把上线首日 API smoke、直报/医院回执、应急指挥值守、安全审计、备份回退待命和机构账号支持纳入 go-live observation gate。默认状态为 watch-ready 计划就绪、实际观察 pending，避免把上线当天真实观察误报为已完成；只有观察窗口、阈值、回退触发条件和值班责任人完整且无当前 critical signal 时，`launch-go-live-observation` 才能通过。
15. 持续开发：新增 `publicHealthLaunchIncidents`、`GET /api/public-health/launch-incidents`、`POST /api/public-health/launch-incidents/:id/actions`、`renderLaunchIncidents`、`buildPublicHealthLaunchIncidentBoard`、`buildStaticLaunchIncidentBoard`、`data-public-health-launch-incident`、`go-live:incident-desk` 和 `publicHealth:launchIncidents`，把上线首日问题分诊、SLA、升级路径、回退决策人、审计记录和 critical open ticket 纳入 launch incident desk gate。默认状态为 desk-ready 待命台账，不代表真实生产事故已关闭；只有 6 条通道完整、回退决策人齐备且无 critical open ticket 时，`launch-incident-desk` 才能通过，最终 production-ready 仍受现场证据、生产交接、P0/P1 阻断项和多方审批约束。
16. Continue development: added `publicHealthLaunchDutyShifts`, `GET /api/public-health/launch-duty-shifts`, `POST /api/public-health/launch-duty-shifts/:id/actions`, `renderLaunchDutyShifts`, `buildPublicHealthLaunchDutyBoard`, `buildStaticLaunchDutyBoard`, `data-public-health-launch-duty-shift`, `go-live:duty-handoffs`, and `publicHealth:launchDutyShifts`. This turns first-day duty windows, primary and backup contacts, command channels, handoff checklists, escalation owners, linked observation windows and linked incident lanes into a launch duty handoff gate. The default state is `roster-ready`, which means the roster is prepared; it does not replace real production staffing evidence, signed handoffs, P0/P1 blocker closure, incident closure, or multi-party approval.
17. Continue development: added `publicHealthLaunchCommandBriefs`, `GET /api/public-health/launch-command-briefs`, `POST /api/public-health/launch-command-briefs/:id/actions`, `renderLaunchCommandBriefs`, `buildPublicHealthLaunchCommandBriefBoard`, `buildStaticLaunchCommandBriefBoard`, `data-public-health-launch-command-brief`, `go-live:command-briefs`, and `publicHealth:launchCommandBriefs`. This turns prelaunch go/no-go, launch start, first receipt, T+8 stability watch and T+24 first-day closure broadcasts into a launch command brief gate. The default state is `briefing-ready`, which means the command brief templates and broadcast paths are prepared; it does not replace real launch-day publication evidence, signed site evidence, production handoffs, P0/P1 blocker closure, critical incident closure, or multi-party approval.
18. Continue development: added `publicHealthSiteEvidenceVerificationTasks`, `GET /api/public-health/site-evidence-verification-tasks`, `POST /api/public-health/site-evidence-verification-tasks/:id/actions`, `renderSiteEvidenceVerificationTasks`, `buildPublicHealthSiteEvidenceVerificationBoard`, `buildStaticSiteEvidenceVerificationBoard`, `data-public-health-site-evidence-verification-task`, `site-evidence:verification-desk`, and `publicHealth:siteEvidenceVerificationTasks`. The desk assigns all nine public-health site-evidence bridge links to owners and commission reviewers. A task can become `verified` only with an existing verified `siteLaunchEvidence` record that matches its template ID; task actions never create source evidence, close P0/P1 blockers, accept production handoffs, or override `site-evidence-required`.
19. Continue development: added `publicHealthLaunchGate.approvalPreflight`, `launch:approval-preflight`, `frontend:launch-approval-preflight`, and `publicHealth:launchApprovalPreflight`. Approval actions now default to `submitted`; a final `approved` decision is rejected until every non-approval launch requirement passes and the caller supplies `APPROVE PUBLIC HEALTH LAUNCH`. The gate records blocked requirement IDs with every action, exposes the preflight state through `GET /api/public-health/launch-gate`, and keeps the interface on `提交审批` until the preflight becomes eligible. This safeguard does not change `site-evidence-required` or manufacture any production approval.
20. Continue development: added `publicHealthStandardImplementationLedger`, `GET /api/public-health/standard-implementation-ledger`, `POST /api/public-health/standard-implementation-ledger/:id/actions`, `renderStandardImplementationLedger`, `buildPublicHealthStandardImplementationBoard`, `data-public-health-standard-implementation`, `standard:implementation-ledger`, and `publicHealth:standardImplementationLedger`. The ledger makes each of the 21 standard domains accountable for owner, source range, data collection, interface mapping, review checklist, gap state, escalation, and an optional verified external evidence reference. Mapping completion and review records improve traceability only; they never manufacture site acceptance, clear P0/P1 blockers, sign a production handoff, or replace the `site-evidence-required` launch gate.

Commission users can now review a mapping, record or escalate a described gap, and select only already verified `siteLaunchEvidence` rows for traceability. The API rejects a gap or escalation without a note and rejects evidence links that are not verified. These actions remain operational traceability records only and never close P0/P1 blockers, sign acceptance, or override `site-evidence-required`.

This is a follow-up warning only; it does not create site evidence, close a P0/P1 blocker, accept a handoff, or alter `site-evidence-required`.

Continue development: added `exchangeExceptionBoard`, `POST /api/public-health/exchange-runs/:id/actions`, `assign-exchange-exception`, `escalate-exchange-exception`, and `resolve-exchange-exception`. Every failed exchange run can now be assigned with an owner and due date, escalated, and resolved only with a compensation receipt ID; all actions require a note and are security-audited. Open exceptions now block the `launch-exchange-receipts` requirement, but no exchange exception action can create site evidence, close a P0/P1 blocker, accept a production handoff, or alter `site-evidence-required`.

Continue development: added command-brief delivery receipt closure to `publicHealthLaunchCommandBriefs`, `POST /api/public-health/launch-command-briefs/:id/actions`, `acknowledge-launch-command-brief`, `escalate-launch-command-brief-receipt`, `acknowledgementTarget`, `pendingAcknowledgementTargets`, and the workbench delivery-receipt controls. Once a command brief has been published, each configured audience can be recorded as acknowledged or escalated with an operator note; unknown audiences, pre-publication receipts, and blank notes are rejected and audited. Delivery receipt tracking is an operational broadcast control only: it never creates signed site evidence, closes P0/P1 blockers, accepts handoffs, or replaces production approval.
