# 多地区部署功能清单与操作指南

## 1. 适用范围

本文用于把同一套卫生健康信息平台部署到多个地区，并保证平台共性能力统一演进、地区差异独立配置、数据与密钥相互隔离、发布物可追溯、故障可回滚。

当前推荐模型是：

```text
同一平台核心版本
  ├─ 地区 A 组合发布 → 地区 A 服务进程 → 地区 A 数据/密钥/域名/接口
  ├─ 地区 B 组合发布 → 地区 B 服务进程 → 地区 B 数据/密钥/域名/接口
  └─ 地区 C 组合发布 → 地区 C 服务进程 → 地区 C 数据/密钥/域名/接口
```

一个 Node.js 服务进程只绑定一个 `REGION_CODE`。当前实现不是“一个进程根据请求动态切换地区”的多租户系统。不同地区必须使用独立进程或独立虚拟机/容器，并隔离数据目录、密钥、外部接口、日志、备份和验收证据。

## 2. 部署原则

1. 平台共性进入核心：统一身份、居民主索引、健康档案、业务流程、安全审计、发布门禁等跨地区稳定能力只维护一份。
2. 地区差异进入地区包：机构、行政区划、地方术语、字典、政策、主题、功能开关、接口参数名称和受控扩展位于 `regions/<regionCode>`。
3. 核心版本统一、地区发布独立：多个地区可以使用同一 Git 提交和平台制品，但每个地区必须生成自己的组合发布清单和激活参数。
4. 运行环境完全隔离：不得跨地区共用业务数据目录、数据库 schema、会话库、对象存储 bucket、OIDC 客户端、短信凭据、接口密钥、审计目录或备份目录。
5. 摘要锁定：部署时从组合发布清单复制地区代码、类别和内容摘要；运行时发现地区文件被修改即拒绝启动。
6. 技术就绪不等于生产批准：`technicalReady=true` 只说明代码、配置、兼容性和摘要通过；联合测试、安全测评、监控、灾备和现场签字未齐时，`productionReady` 仍为 `false`。

### 3.3 当前部署限制

| 限制 | 当前处理方式 |
| --- | --- |
| 一个进程不能服务多个地区 | 每个地区启动独立进程或独立实例 |
| PostgreSQL 业务主存储尚未正式切换 | 已实现四模式核心契约、事务/CAS/outbox 门禁和测试驱动；正式驱动、现场容量和切换仍须验收 |
| 多主机会话需要 PostgreSQL | 设置 `SESSION_TOPOLOGY=multi-host`、`SESSION_STORE=postgres`、`DATABASE_URL` 和 `POSTGRES_SSL_MODE=verify-full` |
| 地区不能由命令自动提升为 production | 完成真实证据与审批后，由 T00 受控评审并提交注册表变更 |
| `productionReady` 当前固定为 false | 现场联合测试、安全/商密、监控、灾备和正式签字不能由本地代码代替 |
| 没有通用 Kubernetes/Helm 生产清单 | 已提供单地区 Docker/Compose 验证模板和 systemd 生成器；生产容器编排仍须结合现场补充 |
| GitHub Pages 不能运行后端 | 仅用于静态页面和脱敏快照演示，不得作为正式业务部署 |

## 4. 推荐拓扑

### 4.1 当前可落地拓扑

每个地区部署一套单主机 Node API 和 SQLite 主存储，前置地区独立的反向代理、TLS 和域名。备份推送到该地区独立的远端受控存储。

```text
地区域名/TLS
    │
反向代理
    │
单地区 Node 进程（REGION_CODE 固定）
    ├─ 独立 DATA_DIR / SQLite
    ├─ 独立密钥环境文件
    ├─ 独立日志与审计保全目录
    ├─ 独立对象存储 bucket
    └─ 地区身份、短信、医院、医保和证照接口
```

在同一物理主机部署多个地区时，至少使用独立系统用户、发布目录、`PORT`、`DATA_DIR`、日志目录、密钥文件和 systemd 服务名。更推荐使用独立虚拟机或容器形成故障与权限边界。

### 4.2 后续扩展拓扑

只有在 PostgreSQL 业务主存储适配器、容量验证、故障切换、原生备份恢复和现场签字全部通过后，才可把单地区扩展成多应用节点。中央 PostgreSQL 会话库并不等于业务数据已经支持多节点。

## 6. 新地区接入操作指南

下列示例使用地区代码 `320100` 和名称“示例市”。正式操作时替换为真实行政区划代码和名称。

### 第一步：预览并创建地区包

先预览，不写文件：

```powershell
npm.cmd run regional:scaffold -- --region=320100 --name=示例市 --parent=320000
```

确认预览后执行事务化创建：

```powershell
npm.cmd run regional:scaffold -- --region=320100 --name=示例市 --parent=320000 --write
```

新地区会以 `enabled=false`、`deploymentClass=test` 进入注册表，不能直接用于生产。

### 第二步：填写地区配置

至少完成：

- `regions/320100/manifest.json`：地区身份、版本、兼容范围、特性和扩展声明。
- `config/organization.json`：卫健委、中心医院、基层机构等业务角色对应的本地机构。
- `config/geography.json`：省、市、区县等行政区角色。
- `config/localization.json`：平台术语和受控历史兼容映射。
- `config/feature-flags.json`：本地区启用的功能。

如有差异，再增加字典、政策、主题、适配器参数等配置。配置中只能保存非敏感值、环境变量名称或证据引用，不能保存口令、令牌、私钥、患者原文和生产凭据。

需要代码扩展时：

1. 在 `manifest.json` 声明扩展 ID、类型、版本、`ownedDomain`、权限和启用状态。
2. 在 `extensions/index.js` 注册同名实现。
3. 不复制平台核心，不在 `server.js` 或业务路由中增加 `if (regionCode === ...)`。

### 第三步：校验草稿

```powershell
npm.cmd run regional:scaffold -- --region=320100 --validate
npm.cmd run regional:check
npm.cmd run regional:test
npm.cmd run regional:hardcodes
```

失败时先修复地区包；不要降低配置契约、硬编码基线或目录安全规则。

### 第四步：进入验证矩阵

先预览生命周期变更：

```powershell
npm.cmd run regional:lifecycle -- enable-test --region=320100
```

确认后写入：

```powershell
npm.cmd run regional:lifecycle -- enable-test --region=320100 --write
```

然后执行：

```powershell
npm.cmd run regional:inventory
npm.cmd run regional:status -- --region=320100
npm.cmd run regional:matrix
npm.cmd run test:all
```

验证环境不得设置 `NODE_ENV=production`。如需生成测试地区组合发布清单，必须显式确认：

```powershell
npm.cmd run regional:package -- --region=320100 --allow-test-region
```

### 第五步：完成现场联调与生产审批

至少归档：

- 真实身份与机构目录联调证据。
- HIS、EMR、LIS、PACS、医保、证照、短信等适用接口的字段映射和回执。
- 地区安全与商用密码评估。
- 监控告警、值班和审计保全证据。
- 数据备份、恢复和 RTO/RPO 演练。
- 地区业务、技术、运维、安全的正式签字。

自动生命周期命令不会提升到 `production`。证据与审批通过后，由 T00 对注册表变更进行评审，把地区类别受控改为 `production`，运行全量门禁并提交唯一集成基线。`deploymentClass=production` 只表示该地区包可进入生产部署审查，不代表自动获得上线授权。

### 第六步：生成无密钥站点部署计划

先参照 `deploy/validation/sites.example.json` 编写站点描述，为每个地区分配独立端口、目录、Bucket、OIDC Client ID、服务名和系统账号：

```powershell
npm.cmd run regional:deploy-plan -- `
  --descriptor=deploy/validation/sites.example.json
```

确认预览后生成制品：

```powershell
npm.cmd run regional:deploy-plan -- `
  --descriptor=deploy/validation/sites.example.json `
  --write
```

输出位于 `release/deployments/<deploymentId>/`。生成器把计划绑定到 Git 提交、核心身份摘要、地区内容摘要和组合发布摘要；任一资源冲突都会阻断。

## 7. 生成地区发布物

对获准的生产地区执行：

```powershell
npm.cmd run regional:status -- --region=320100
npm.cmd run regional:package -- --region=320100
npm.cmd run deployment:package -- --strict --release-id=<approved-release-id>
npm.cmd run deployment:verify
```

关键输出：

- `release/regions/320100/composite-release.json`：平台版本、地区版本、地区内容、文件摘要、组合 `releaseId` 和激活参数。
- `release/production-deployment-package.json`：平台运行文件清单、整体制品摘要、进程和回滚契约。
- `release/production-deployment-package.md`：供人工复核的部署清单。

地区组合发布清单与平台部署清单必须成对归档。前者锁定“部署哪个地区”，后者锁定“部署哪些运行文件”。

不得手工计算激活参数。应从 `composite-release.json` 的 `activation` 原样复制：

```text
REGION_CODE=320100
REGION_DEPLOYMENT_CLASS=production
REGION_CONTENT_DIGEST=sha256:<组合发布清单中的实际摘要>
```

## 8. 每个地区的环境准备

每个地区创建独立、不得提交到仓库的密钥环境文件。最小结构如下：

```text
NODE_ENV=production
PORT=<地区独立端口>

REGION_CODE=<地区代码>
REGION_DEPLOYMENT_CLASS=production
REGION_CONTENT_DIGEST=sha256:<组合发布摘要>

STORAGE_ENGINE=auto
DATA_DIR=<地区独立持久化目录>
SQLITE_JOURNAL_MODE=WAL
SQLITE_SYNCHRONOUS=FULL
SQLITE_BUSY_TIMEOUT_MS=5000

SESSION_STORE=sqlite
SESSION_TOPOLOGY=single-host
SESSION_SECRETS=<由密钥系统注入>

DEPLOYMENT_SECRET_PROVIDER=<vault|kms|orchestrator>
DEPLOYMENT_RELEASE_ID=<批准的发布编号>
DEPLOYMENT_ARTIFACT_DIGEST=sha256:<平台部署制品摘要>
DEPLOYMENT_APP_DIR=<该地区只读发布目录>
DEPLOYMENT_SECRET_ENV_FILE=<该地区密钥文件或挂载点>
DEPLOYMENT_DATA_DIR=<该地区数据目录>
DEPLOYMENT_LOG_DIR=<该地区日志目录>
```

此外按 `.env.example` 配置该地区独立的 OIDC、短信、医院接口、对象存储、支付、医保、证照、SIEM、告警、审计和切换签字变量。

同机部署两个地区时，禁止出现以下重复：

- `PORT`
- `DATA_DIR` / `DEPLOYMENT_DATA_DIR`
- `DEPLOYMENT_APP_DIR`
- `DEPLOYMENT_SECRET_ENV_FILE`
- `DEPLOYMENT_LOG_DIR`
- 数据库或会话 schema
- 对象存储 bucket
- OIDC client ID 和回调地址
- 接口签名、短信、金融和审计密钥

## 9. 部署和启动

### 9.1 部署前

```powershell
npm.cmd run regional:status -- --region=<地区代码>
npm.cmd run deployment:verify
npm.cmd run env:check:production
npm.cmd run deploy:check:full
npm.cmd run release:report:full
npm.cmd run storage:backup
```

确认已保存：

- 当前版本与上一版本的平台部署清单。
- 当前版本与上一版本的地区组合发布清单。
- 当前环境文件的变量名清单与密钥版本号，不保存密钥值。
- 部署前数据备份及 SHA-256 清单。
- 变更单、窗口、负责人、回滚阈值和 Go/No-Go 结论。

### 9.2 systemd 部署

以 `deploy/chronic-care-platform.service.template` 为基础，为每个地区生成独立单元，例如：

```text
chronic-care-platform-320100.service
chronic-care-platform-210200.service
```

替换服务用户、用户组、只读发布目录、密钥环境文件、数据目录和日志目录。不同地区不要使用同一个系统用户和可写目录。启动命令保持：

```text
/usr/bin/node server.js
```

### 9.3 启动后验证

```powershell
Invoke-RestMethod https://<地区域名>/api/live
Invoke-RestMethod https://<地区域名>/api/health
Invoke-RestMethod https://<地区域名>/api/regional/context
npm.cmd run launch:smoke -- --base-url=https://<地区域名>
```

逐项确认：

- `/api/live` 返回成功。
- `/api/health` 返回成功且关键依赖就绪。
- `/api/regional/context` 的 `regionCode`、`deploymentClass` 和 `contentDigest` 与组合发布清单一致。
- 登录、角色范围、首页品牌、机构和行政区展示正确。
- 该地区适用的核心业务冒烟通过。
- 身份、短信、医院、医保、证照、对象存储、告警和审计链路按现场范围通过。
- 监控已收到该地区实例的指标，告警路由能够到达本地区值班人员。

## 10. 多地区批量发布顺序

不要同时首次切换所有地区。推荐顺序：

1. 通用模板门禁通过。
2. 选择一个非生产验证地区验证组合包和部署自动化。
3. 选择一个已批准地区灰度上线。
4. 观察完整业务周期、告警和备份任务。
5. 按地区逐个推进，每个地区独立作出 Go/No-Go 决策。
6. 任一地区失败时只停止该地区发布，不回退其他已验证地区。

代码库内可先执行第二地区复制演练：

```powershell
npm.cmd run regional:replication
```

该演练使用 `210200` 和合成验证地区 `990001`，验证同一核心、地区配置差异、运行激活锁、资源隔离、发布登记和运维清单。它不代替第二个真实地区的现场数据和审批。

批量发布台账至少记录：

| 字段 | 示例 |
| --- | --- |
| 平台 Git 提交 | `<40位提交摘要>` |
| 平台制品摘要 | `sha256:<digest>` |
| 地区代码 | `320100` |
| 地区组合 releaseId | `core-...-region-320100-...` |
| 地区内容摘要 | `sha256:<digest>` |
| 环境 | staging / production |
| 部署时间 | ISO-8601 |
| 操作人/复核人 | 受控身份 |
| 备份编号 | `<backup-id>` |
| 冒烟报告 | `<evidence-ref>` |
| Go/No-Go | Go / No-Go |

## 11. 回滚指南

### 11.1 只回滚应用

适用于代码或地区配置问题，且新版本没有产生不兼容数据变化：

1. 停止该地区服务。
2. 切换到上一版只读平台发布目录。
3. 恢复上一版地区组合发布清单对应的三个激活变量。
4. 保持数据不变。
5. 启动并检查 live、health、地区上下文和核心业务。
6. 记录回滚原因、版本摘要、操作人和验证证据。

### 11.2 同时回滚数据

只有在明确发生不兼容写入或数据损坏时执行：

```powershell
npm.cmd run rollback:snapshot -- "data/backups/<备份目录>"
```

该命令会先创建 `pre-rollback` 安全副本。正式环境还应按实际 `DATA_DIR` 和数据库备份规范执行恢复；不要把仓库默认相对路径误当成生产数据目录。

数据回滚前必须确认业务停写、备份摘要、恢复点、影响时间窗和责任人。不得为了修复展示或配置问题直接回滚业务数据。

## 12. 常见失败与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 地区不存在或未启用 | 未注册或仍为 draft | 检查 `regional:inventory`，按生命周期进入 validation |
| 测试地区在生产启动失败 | `deploymentClass=test` | 不得绕过；完成证据和 T00 受控生产评审 |
| 地区类别不一致 | 环境变量与注册表不一致 | 从同一组合发布清单重新复制 activation |
| 地区内容摘要不一致 | 地区文件在打包后被修改 | 禁止现场热改；重新评审、打包、验证和发布 |
| 地区矩阵失败 | 配置契约、扩展或兼容性错误 | 修复地区包并重新运行窄测试和全量矩阵 |
| `env:check:production` 失败 | 缺少真实配置或仍是占位值 | 补齐密钥系统、身份、接口、审计和现场签字 |
| `/api/health` 返回 503 | 存储或中央会话依赖不可用 | 检查该地区数据库、目录权限和会话库 |
| 页面地区名称错误 | 页面绕过地区上下文或配置错误 | 修复配置或调用方式，禁止页面硬编码 |
| 一个地区影响另一个地区 | 共用了目录、数据库、端口或密钥 | 立即隔离资源，审计数据和凭据影响范围 |
| 部署包通过但仍不能上线 | 仅技术证据通过 | 继续完成外部接口、安全、灾备和现场签字 |

## 13. 上线验收清单

### 制品

- [ ] 平台 Git 提交已批准并固定。
- [ ] 平台部署清单验证通过。
- [ ] 地区组合发布清单验证通过。
- [ ] 激活变量来自同一组合发布清单。
- [ ] 上一版本制品和组合发布清单可用。

### 隔离

- [ ] 地区发布目录、数据目录、日志目录和密钥文件独立。
- [ ] 地区数据库/会话 schema 和备份独立。
- [ ] 地区对象存储、OIDC、短信和接口凭据独立。
- [ ] 域名、TLS、端口和监控标签不会与其他地区混淆。

### 门禁

- [ ] `regional:check`、`regional:test`、`regional:matrix` 通过。
- [ ] `deployment:verify`、`env:check:production` 通过。
- [ ] `deploy:check:full`、`release:report:full` 通过或外部阻断项有正式处置结论。
- [ ] 现场联合测试、安全/商密、监控和灾备证据齐全。
- [ ] Go/No-Go 多方签字已归档。

### 上线后

- [ ] live、health、地区上下文和核心业务冒烟通过。
- [ ] 指标、日志、告警和审计进入正确的地区通道。
- [ ] 备份任务成功且可查询摘要。
- [ ] 回滚观察期和负责人已明确。
- [ ] 未把 `productionReady=false` 的本地技术状态误写为现场生产验收结论。

## 14. 日常运维清单

每日：

- 检查各地区 `/api/live`、`/api/health`、告警、失败接口、死信和备份结果。
- 核对监控标签和告警接收方，防止跨地区串线。

每次发布：

- 运行地区清单和矩阵，固定平台摘要、地区摘要和现场证据。
- 逐地区发布、观察和决定是否继续下一个地区。

每月：

- 抽查备份恢复、会话清理、证书/密钥到期、接口凭据轮换和审计保全。
- 复核地区扩展是否仍有必要，能沉淀为共性的能力应回归平台核心。

每季度或重大变更后：

- 执行恢复演练、故障切换演练、权限复核和地区数据隔离审计。
- 对各地区版本差异进行收敛，避免形成长期分叉代码库。

可生成离线运维就绪报告：

```powershell
npm.cmd run regional:operations
npm.cmd run regional:configuration
npm.cmd run regional:evidence
npm.cmd run regional:dossier
```

管理端运行时可访问 `GET /api/regional/deployments` 查看最小化实例清单，并通过 `GET /api/regional/deployments/:regionCode/dossier` 查看单地区投产档案。执行探测时只能调用 `POST /api/regional/deployments/:regionCode/probes`，请求体和查询参数均须为空，目标地址由 `REGIONAL_SITE_<地区代码>_BASE_URL` 在服务端配置。投产档案接口同样拒绝查询参数，只返回摘要、状态、门禁和稳定阻断码，不返回站点地址、配置值、密钥或证据正文。

最近一次受控备份完成时间由服务端 `REGIONAL_SITE_<地区代码>_BACKUP_CHECKED_AT` 提供。探测回执会同时检查地区代码、部署类别、内容摘要、健康状态、证书有效期和备份新鲜度；客户端不能提交或覆盖这些证据。
