# ADR：模块化单体与微服务提取标准

状态：已采纳  
日期：2026-08-03

## 决策

平台继续采用模块化单体。物理进程不是领域边界的默认实现，只有候选模块同时满足以下条件才允许提取为独立服务：

1. 独立扩缩容、故障隔离、数据自治至少各 3 分；
2. 六项评分合计至少 18 分；
3. 已有独立负责团队、发布节奏和可值守的运行手册；
4. Repository、版本化契约、事务型 Outbox、幂等 Inbox、关联 ID 和依赖健康指标已经在线运行；
5. 不存在站点证据、数据归属、SLO 或安全验收阻断项。

评分范围为 0–5，唯一机器可读基线是
`config/service-extraction-scorecard.json`。任何提取决策必须通过架构测试，不能仅凭代码量、路由数量或技术偏好。

## 当前结论

集成、公共卫生和临床专科均保持模块化单体。它们已形成可独立验证的能力单元，但数据自治、生产证据和运维成熟度尚未同时达标。保持进程内调用可减少分布式事务、网络故障和重复值守成本。

## 提取顺序

达到门槛后，按以下顺序实施：

1. 固化输入/输出契约与兼容窗口；
2. 建立独立数据迁移和双读校验；
3. 通过 Outbox 复制事件，不做跨库双写；
4. 影子流量和故障注入验证；
5. 小流量切换并保留可逆回退；
6. 生产证据完整后移除单体内旧实现。

## 后果

- 领域模块可以按不同进程分工开发，但集成仍通过同一主干和同一门禁。
- `shared` 与 `state-data` 只能承担组合、查询或适配职责，不得成为业务数据所有者。
- 生产 Go/No-Go 继续依赖真实环境和签名站点证据。
