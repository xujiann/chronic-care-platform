# 卫生健康信息平台建设要求研究与下一步开发规划

生成日期：2026-07-16

本文面向 `chronic-care-platform` 主工程，综合仓库内申报材料拆解、现有研发报告、生产上线要求、数据治理底座、公共卫生/体检/院前急救/互联网护理/医保协同等模块文档，以及国家卫生健康信息化、互联互通、健康医疗大数据和网络安全相关要求，形成下一阶段开发规划。

## 一、建设要求归纳

### 1. 区域全民健康信息平台和互联互通

区域全民健康信息平台的核心不是单一业务系统，而是以电子健康档案和区域平台为核心，围绕数据资源标准化、互联互通标准化、基础设施、应用效果和现场查验建立可测评体系。对本项目的直接要求是：

- 建立居民主索引、电子健康档案、共享文档、交互服务和跨机构应用。
- 对健康档案数据集、共享文档、交互服务做可机读、可复测的标准符合性证据。
- 平台必须能支撑医疗服务、公卫服务、卫生综合管理、居民自助服务和平台内外机构接入。
- 现场查验、文件审查、演示答疑、生产环境运行证据必须和代码能力分开管理。

### 2. 数据标准、主数据和数据治理

平台应持续对齐健康档案基本数据集、出生医学证明、死亡医学证明、区域平台技术规范、共享文档规范、居民健康卡、疾病分类与代码、手术操作分类、药品耗材代码等标准。落到开发侧，应建立：

- 居民主索引 `personIndex` 与居民、家庭、授权、健康档案、诊疗记录、体检、急救、护理、医保等业务记录的一致性检查。
- 机构、科室、人员、疾病、手术、药品、耗材、检查、检验、影像、体检项目、急救事件等主数据版本管理。
- 标准字典和地方扩展字典的差异、版本、责任人、审批、回滚和现场签字。
- 从 HIS、EMR、LIS、PACS、医保、公卫、体检、急救、互联网护理等来源到平台集合的字段映射、血缘、幂等、签名、质量规则和阻塞项。

### 3. 业务应用范围

平台应同时覆盖助医、惠民、辅政、科研和区级实施：

- 助医：分级诊疗、转诊会诊、影像/心电/检验共享、临床辅助、检查检验互认。
- 惠民：统一居民入口、电子健康档案、电子病历摘要、授权共享、固定取药、预约挂号、护理、陪诊、体检、出生/免疫等全生命周期服务。
- 辅政：综合驾驶舱、统计质控、医疗质量安全、机构信用、医保协同、公卫事件、运行监测。
- 科研：专病库、多模态数据集、伦理审批、脱敏授权、沙箱访问、成果回流。
- 区级实施：区属医院、基层、妇幼、体检、急救、医保、疾控和公卫专项系统接入。

### 4. 安全合规和生产上线

当前系统可以做演示和试运行准备，但正式生产上线必须满足：

- 等保、密评、商用密码、信创适配、生产密钥、日志留存、SIEM、漏洞扫描、权限穿透测试。
- 真实身份源、短信/移动端、HIS/EMR/LIS/PACS、医保、电子证照、疾控直报、120 CTI、对象存储、监控、灾备均需现场联调证据。
- `data/db.json` 只能作为演示快照或迁移来源，生产应使用受控数据库、备份恢复、审计归档和附件对象存储。
- 所有未真实接入事项必须保留 `external blocked` / `onsite blocked` / `productionReady=false`，不能用本地 readiness 通过替代现场验收。

## 二、现有系统落点

当前平台已经形成以下可继续扩展的基础：

- 统一角色入口：居民、机构、医生、医保、区县/医共体、卫健委、护理、科研、运维。
- 主数据与档案：`residents`、`personIndex`、`personalRecords`、`diagnosticReports`、授权、访问日志和居民健康档案。
- 数据治理：`data-governance:readiness`、数据资产、标准字典、血缘、质量规则、平台总线。
- 接口治理：`integrationContracts`、`interface:mapping`、签名、幂等、字段映射、失败补偿、现场阻塞。
- 发布证据：`release:manifest`、`platform:capability-map`、`release:report`、`deploy:check`、`launch:smoke`。
- 重点业务：慢病、公卫、免疫、妇幼、互联网护理、陪诊、挂号、体检、院前急救、血液、医保、影像云、质量安全、科研沙箱、生产运维。

主要差距：

- 能力广，但部分模块仍是演示闭环，缺少真实外部回执、失败样例、压测和签字。
- `server.js` 仍过大，继续叠加模块会增加回归风险。
- 主数据目录已经有入口，但字典版本、差异审批、现场签字和回滚还不够产品化。
- 服务订单、消息、评价、投诉、待办在护理、陪诊、挂号、体检、急救、家医、慢病之间仍有重复建模。
- 外部阻塞项已经进入能力总览风险聚合，但还需要形成统一 blocker API、责任流转和证据包闭环。

## 三、下一步开发规划

### P0：统一阻塞项和服务订单底座

1. 外部阻塞项统一台账
   - 目标：把 HIS/EMR/LIS/PACS、医保、疾控、120、电子证照、短信、身份源、对象存储、SIEM、灾备等阻塞项统一到一个 API 和页面。
   - 产出：`/api/platform/blocker-register`、平台页阻塞项工作台、证据包上传/登记结构、release report 聚合。
   - 验收：`platform:capability-map` 能显示来源、P0/P1、责任方、现场窗口、下一步动作；`release:report` 可按 blocker 汇总。

2. 统一服务订单与消息中心
   - 目标：把护理、陪诊、挂号、体检异常、急救回访、家医签约、慢病随访统一为可查询、可评价、可投诉、可审计的服务订单模型。
   - 产出：`serviceOrders` 聚合层、居民端服务中心、机构端处置中心、卫健委监督中心。
   - 验收：居民端只看本人/授权家庭；机构端只看本机构；监管端看聚合统计和异常。

3. 主数据目录二期
   - 目标：机构/科室/人员、疾病/手术、药品/耗材、检查/检验/影像、体检项目、急救事件编码进入版本化管理。
   - 产出：`/api/data-governance/master-data`、字典版本差异、发布/回滚/签字证据。
   - 验收：字段映射和业务模块引用同一版本，缺失映射必须生成 blocker。

### P1：重点业务试点闭环

1. 体检异常到慢病/家医闭环
   - 将体检异常项自动触发慢病风险分层、家医建议、居民待办、机构复核和随访结果。
   - 补齐批量导入、撤回更正、报告附件、居民异议处理。

2. 院前急救试点闭环
   - 以 1 个急救中心、2 台车辆、1-2 家医院为最小试点。
   - 补齐 CTI/录音、定位、车载设备、急诊预建档、电子交接、弱网补偿和首日观察。

3. 公卫/免疫/妇幼事件链
   - 出生、儿童保健、免疫、传染病直报、死亡证明、公卫随访形成全生命周期事件链。
   - 补齐疾控直报、免疫规划、冷链、AEFI、家长授权和跨区接种归并。

4. 医保协同深化
   - 大连市医保局、大连市医保中心、区市县医保局按政策、经办、属地监管分别建看板和流程。
   - 补齐结算字段、待遇资格、电子凭证、目录版本、基金监管、药耗监管和最小化共享审批。

### P2：生产化和架构治理

1. 领域路由拆分
   - 按体检、急救、医保、公卫、慢病、血液、发布证据等拆出 router/service，保持 API 路径兼容。
   - 每次只拆一个领域，先补测试再迁移。

2. 生产数据库和对象存储切换
   - 完成 PostgreSQL 主读/写入适配、影子核对、回滚演练、受控附件存储、病毒扫描、生命周期和授权下载。

3. 安全合规门禁
   - 将等保、密评、商密设备、生产密钥、SIEM、漏洞扫描、权限测试、灾备演练纳入统一上线 gate。

4. 指标中心和整改闭环
   - 建立“指标 -> 明细 -> 事件 -> 整改 -> 复核”链路，覆盖卫健委驾驶舱、医共体绩效、居民服务运营、医保协同、公卫事件、急救响应、体检异常。

## 五、固定开发规则

1. 平台优先：新功能必须接入现有角色、API、数据、readiness、release/deploy 和文档链路。
2. 最小权限：所有居民、机构、医保、卫健委、科研、运维数据必须按角色裁剪。
3. 主索引优先：居民相关数据必须能追溯到 `personIndex` 或稳定居民标识。
4. 外部接口诚实标注：未真实联调的接口必须保留现场阻塞状态。
5. 证据闭环：页面、API、数据、审计、readiness、测试、release/deploy 至少形成一条完整链。
6. 小步可验收：每次只做一个可运行、可测试、可报告的小切片。
7. 保护运行态数据：预览和探测优先临时 `DATA_DIR`，避免把噪声写入 `data/db.json`。
8. 文档即门禁：重要架构、边界、上线条件、现场阻塞项必须有文档并被测试或 readiness 覆盖。

## 六、建议下一轮立即执行

下一轮开发建议直接做“平台阻塞项统一台账”：

- 从 `platformCapabilityMap.riskRegister` 生成统一 blocker register。
- 新增 `/api/platform/blocker-register`。
- 平台页增加筛选、责任方、P0/P1、现场窗口、证据状态和下一步动作。
- `release:report` 增加 blocker summary。
- 测试覆盖 API、静态页面、builder、release/deploy。

这一步能把当前“知道有风险”推进到“风险可办理、可验收、可发布取证”，是从演示平台走向试点平台最关键的底座。
