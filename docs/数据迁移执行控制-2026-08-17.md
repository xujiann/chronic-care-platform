# 数据迁移执行控制

## 目标

本批次把既有“迁移、对账、回滚和质量”控制中心向执行侧推进，但不改变生产授权边界。实现只处理集合名、批次号、事务号、序列、计数和 SHA-256 摘要，不保存患者数据、机构原始报文、凭据或租约原值。

## 执行链

1. 控制面按迁移波次创建批次计划，并在同一事务中写入 `planned` 元数据 outbox 事件。
2. 后台工作器领取有时限的租约。存储侧只保留工作器与租约的 SHA-256 摘要，以租约版本隔离并发和过期工作器。
3. 工作器只消费已经提交的本地 outbox 范围；严禁在业务请求路径向目标库双写。
4. 每个 checkpoint 必须同时推进源 outbox 序列和已应用事件数。进程崩溃后释放过期租约，但保留最后一个 checkpoint。
5. 完整覆盖计划范围后进入待对账状态；源目标计数、摘要、重复数、差异数及 checkpoint 必须精确一致。
6. 执行侧对账通过后，还必须绑定既有控制中心的 `local-candidate` 记录，并验证相同 run、wave 和 checkpoint，才能形成执行侧本地候选。

## 状态

`pending → leased → applying → awaiting-reconciliation → reconciled → local-candidate`

异常退出通过 `leased/applying → pending` 恢复，checkpoint 不回退。超过最大崩溃恢复次数后进入 `recovery-exhausted`，需要离线处置，不能自动继续。

## 安全边界

- 输入上下文必须是 `background-worker`；`request-path` 会直接返回阻断错误。
- 计划幂等键复用但摘要漂移会被拒绝。
- checkpoint 只能单调前进，旧租约版本不能覆盖新租约。
- 对账失败不会改变批次状态，也不会生成候选。
- `local-candidate` 仅表示本地技术门禁通过；所有结果固定为 `productionReady: false`、`productionPrimary: false`、`activationAuthorized: false`。
- 真实全量演练、签名对账、回滚演练、容量与容灾、现场变更审批仍是外部证据，仓库代码不能替代。

## 验证

```powershell
node --test test/data-migration-execution-runtime.test.js
node scripts/data-migration-execution-readiness.js
npm run process:verify
```

就绪脚本可用 `--input=<恢复状态文件> --output=<报告路径> --write` 检查持久化的元数据恢复快照。报告通过也不会授权生产。
