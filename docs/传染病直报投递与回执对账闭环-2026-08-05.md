# 传染病直报投递与回执对账闭环

日期：2026-08-05  
迭代：迭代 3  
实现模块：`public-health-direct-report-reconciliation-service.js`

## 1. 目标与边界

本迭代提供传染病直报投递与回执的纯领域对账能力，覆盖异常发现、责任分派、确认、补偿、独立复核和关闭。模块不发送直报、不接收网络回调，也不改变直报 Worker、路由或中心运行时装配。

生产边界保持不变：

- 所有扫描结果、对账工单和查询投影的 `productionReady` 固定为 `false`。
- 仓库内的合成测试和技术门禁不能代替现场联调、正式回执、生产授权或 Go/No-Go 决策。
- 模块不保存原始请求/响应报文、居民或患者身份、姓名、电话、地址、凭据、令牌、密钥和签名。
- 只保存业务记录引用、异常类型、SHA-256 指纹、角色、受控证据引用及审计摘要。

## 2. 输入投影

扫描函数只接收三类最小投影：

| 投影 | 必需字段 | 可选字段 |
|---|---|---|
| case | `id`、`state` | `version`、`updatedAt` |
| delivery | `id`、`caseId`、`state` | `version`、`updatedAt`、`nextAttemptAt`、最小 `providerReceipt` |
| receipt | `id`、`deliveryId`、`caseId`、`status`、`receivedAt`、`receiptDigest` | 无 |

`receiptDigest` 必须是 SHA-256。输入对象任意层级出现 `payload`、原始正文、居民/患者身份、凭据、令牌、私钥或签名字段时，扫描立即失败，不执行“清洗后继续”。

## 3. 异常判定

`scanDirectReportReconciliation` 使用固定时刻和超时阈值生成确定性结果：

| 异常类型 | 判定示例 | 严重度 |
|---|---|---|
| `missing-receipt` | 投递处于 `awaiting-callback`，但没有最小回执投影 | medium |
| `state-drift` | 回执状态与投递状态冲突、工单状态未同步、case/delivery/receipt 绑定断裂 | critical |
| `duplicate-receipt` | 同一投递出现两个不同的回执 ID/摘要；完全相同的重复采集按幂等重放处理 | high |
| `timeout` | 等待回调超时、租约停滞、重试计划已过期 | high |
| `dead-letter` | 投递进入死信状态 | critical |

每项异常由类型、case 引用、delivery 引用、异常细节和最小源投影摘要生成稳定 `findingDigest`。相同输入和相同时刻产生完全相同的排序、编号及摘要。

## 4. 对账状态机

```text
discovered
  └─ assign ─> assigned
                 └─ acknowledge ─> acknowledged
                                      └─ compensate ─> compensated
                                                           └─ review ─> independently-reviewed
                                                                          └─ close ─> closed
```

统一控制：

1. 每个动作必须提交 `expectedVersion`，版本不一致返回 CAS 冲突。
2. 每个动作必须提交 `idempotencyKey`；仅保存键摘要。相同键和相同动作可重放，相同键绑定不同意图时拒绝。
3. `actorRole` 只能来自受控角色表：委级运维、疾控业务、接口运维、医院信息中心、上游运维、疾控审计和安全审计；不能通过任意字符串自授权。
4. `assigneeRole` 只能是接口运维、医院信息中心或上游运维，`acknowledge` 和 `compensate` 只能由被分派角色执行。
5. 补偿策略只允许：重新查询回执、重放投递、修正投影、隔离重复回执、升级至上游机构。
6. 补偿、复核和关闭必须绑定 `evidence://`、`cmdb://`、`audit://`、`runbook://`、`ticket://` 或 `drill://` 受控引用及 SHA-256 摘要。
7. 复核角色和复核人必须独立于确认/补偿人，且必须显式 `approved: true`。
8. 关闭必须在独立复核后执行，并提交精确命令 `CLOSE DIRECT REPORT RECONCILIATION`。

状态机不直接重放投递或修改 case。它记录已经由有权运行时完成的补偿结果，避免在对账领域内形成第二写入源。

## 5. 持久化与审计

`discoverDirectReportReconciliationCases` 只持久化：

- 异常、源投影和动作的 SHA-256 摘要；
- case/delivery 受控引用；
- 当前状态、版本、分派角色和补偿策略；
- 证据引用和证据摘要；
- 动作时间、角色、操作者摘要和动作摘要。

每条审计摘要同时保存 `previousDigest` 和 `eventDigest`。首条记录绑定全零创世摘要，后续记录绑定前一条 `eventDigest`，形成连续 SHA-256 哈希链。`verifyDirectReportReconciliationAudit` 校验序号、前序摘要和事件摘要；发现任一历史记录被修改时，所有后续状态动作和公共投影都 fail-closed。

审计摘要不保存操作者明文 ID。公共查询使用 `projectDirectReportReconciliationCase` 和 `summarizeDirectReportReconciliations`，不会返回源摘要、证据摘要、操作者摘要、审计链摘要或幂等键摘要。

## 6. 集成交接

后续由集成进程按所有权边界完成：

1. T03 从现有 case、delivery 和可信回执生成上述最小投影。
2. 持久化集合使用 `publicHealthDirectReportReconciliationCases`，写入仍须经过平台状态仓储事务。
3. T00 负责中心运行时依赖注入、部署调度和全局发布门禁；如需 API，T03 只在公共卫生归属路由内接线。
4. 门户只展示公共投影；不能展示原始回执、证据内容、签名、摘要或提供绕过状态机的“直接关闭”入口。
5. 真实补偿命令由既有 Worker/运维运行时执行，对账模块只登记受控结果及独立复核。

## 7. 验收

- 五类异常均有确定性测试。
- 完全相同的回执采集不误报为重复回执。
- case/delivery/receipt 绑定断裂可被发现。
- 所有状态迁移、CAS、幂等冲突、受控角色表、角色所有权、证据门禁、独立复核和关闭确认均有测试。
- 审计摘要连续哈希链可验证，历史记录或链关系篡改会阻断动作和查询。
- 持久化对象和公共投影不包含原始报文、居民身份、凭据或签名。
- `productionReady` 始终为 `false`。
