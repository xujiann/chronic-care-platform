# ADR：审计链失败语义与兼容迁移

- 状态：Accepted
- 日期：2026-08-19
- Owner：T00（组合根与发布门禁）+ T01（身份安全）+ 审计/留存 Owner
- 影响范围：审计哈希链、`/api/audit/verify`、安全合规报告、全量状态兼容写入、留存报告与发布门禁

## Problem

主线在 `server.js` 与 `scripts/audit-retention.js` 各维护一份 `verifyAuditTrail`。两份实现都有三项相同语义：

1. `passed` 只检查 `broken.length === 0`，`linkBroken` 仅作为诊断返回；
2. 行内容哈希不一致时，只有字段文本包含 `tampered` 或哈希缺失才进入 `broken`，普通字段篡改可能继续通过；
3. `/api/audit/verify` 与安全合规报告会先对 `dataAccessLogs` 调用 `resealAuditTrail`，全量 `PUT /api/state` 也可能依据宽松结果重封链。

因此当前“通过”既不保证每行内容哈希有效，也不保证前后链接连续；读取时重封还可能覆盖原始异常。现有测试明确锁定“链接漂移只诊断不失败”，并只用包含 `tampered` 的文本验证内容篡改。

2026-08-19 对跟踪种子的只读采样显示：`securityEvents` 120 行、`dataAccessLogs` 10 行，当前哈希不匹配、缺失哈希和链接漂移均为 0。严格语义可直接覆盖当前演示种子，但无法据此推定外部运行环境、历史导出或留存副本同样干净。

需要决定：什么条件构成审计链通过，发现异常时 API、写入、报告和发布门禁如何失败，以及旧链如何在不销毁原始证据的前提下迁移。

## Options

1. **维持诊断语义。** 保持 `broken` 与 `linkBroken` 分离，只有缺失哈希或带特定文本的篡改才失败。
2. **原地立即切换严格语义。** 任意行哈希或链接不一致都令 `passed=false`，删除所有验证前重封，不提供旧链迁移期。
3. **版本化严格语义并受控迁移旧链。** 建立唯一 v2 验证器；严格失败，同时对既有非合规链提供离线盘点、原始摘要封存、独立审批和一次性基线迁移。
4. **立即以外部不可变审计平台替换本地链。** 停止本地哈希链作为主证据，改由 SIEM/WORM 或专用审计服务承载。

## Advantages

- **方案 1：** 无兼容变化，实施成本最低。
- **方案 2：** 语义简单，最快消除静默通过和读取时重封。
- **方案 3：** 同时获得 fail-closed 语义、公共契约可控演进和历史证据可追溯迁移；当前干净种子无需数据变更。
- **方案 4：** 长期可获得独立留存、访问控制和更强的防抵赖能力。

## Disadvantages

- **方案 1：** 继续把不完整链报告为有效，不满足现行治理规则。
- **方案 2：** 外部环境若有遗留链漂移，会立即阻断写入、报告和发布门禁；缺少盘点与恢复路径。
- **方案 3：** 需要共享验证模块、兼容契约、迁移工具、运行手册和多角色审批，实施范围最大。
- **方案 4：** 引入新外部依赖、采购和运维责任；外部系统不可用时仍需本地安全失败语义，不能直接消除本问题。

## Migration cost

推荐方案 3，成本为高：

- 抽取一个由运行时与留存脚本共用的版本化验证器，消除两份重复实现；
- 保持 `GET /api/audit/verify` 的 HTTP 200 与 `passed/trails` 主体兼容，同时增加稳定的验证版本、失败分类和可运维错误码；
- 删除验证路径中的 `resealAuditTrail`，所有追加操作先验证既有链，异常时拒绝写入且不改写原始行；
- 对历史环境先执行只读 preflight，输出行数、首尾摘要和失败分类，不输出审计正文；
- 旧链确需迁移时，封存原始导出摘要并经独立审批，在请求路径之外建立带来源摘要的新 genesis/baseline 事件；禁止无证据静默重封；
- 更新 API、合规报告、留存 CLI、发布门禁、升级/回滚说明和负向测试。

## Risk

- 严格门禁可能暴露此前被掩盖的历史漂移并阻断全量状态兼容写入或发布流程。
- 若迁移工具重算后覆盖原始链，会永久丢失异常证据；必须先封存原始摘要并保持迁移不可逆记录。
- 兼容期若保留“旧语义通过”开关，风险会长期化；不得设置生产降级开关。
- 当前 SHA-256 链只能检测未重新计算的变更，不能单独证明操作者身份或防止有写权限者重算整链；外部不可变留存和签名仍是独立生产要求。
- 延迟决策会继续允许合规报告和发布证据误报有效。

## Recommendation

推荐方案 3，并要求：

1. v2 的 `passed` 仅在每行内容哈希、每个前序链接和结构约束全部有效时为 `true`；不得依赖文本关键词识别篡改。
2. 验证、读取和报告路径不得重封或修复链；修复只能是独立、留痕、经审批的迁移操作。
3. API 业务结果失败保持可解析响应，但合规报告、留存 CLI、发布与生产 Go/No-Go 必须 fail-closed。
4. 全量状态兼容写入不得借重封接受被修改的审计行；具体拒绝状态码和未修改历史行兼容策略需在实现 PLAN 中锁定。
5. 实施前由 T00、T01 与审计/留存 Owner 共同批准 API 兼容、历史 preflight、迁移证据和回滚方案。
6. 最低测试包括：普通字段篡改、首/中/尾链接断裂、缺失/格式错误哈希、重排/删除/插入、空链、读取不变性、全量写入拒绝、CLI 非零退出及发布门禁传播。

## Implementation

2026-08-20 的 P0 主线迁移按用户明确批准实施方案 3：

- `src/identity-security/audit-chain.js` 成为运行时和留存 CLI 共用的 v2 验证器；任意内容哈希、前序链接、重复/缺失 ID、无效哈希格式或非数组结构都会使 `passed=false`。
- `GET /api/audit/verify` 与合规报告保持 HTTP 200 和原有主体兼容，但不再在验证前重封 `dataAccessLogs`。
- `PUT /api/state` 将两条审计链视为服务端管理字段：调用方可以省略；若提交则必须与当前服务端值完全一致。任何删除、插入、重排、链接修改或内容修改均返回稳定错误码且不写业务数据。
- 版本冲突先于审计字段比较返回原有 `409 STORAGE_CONFLICT`，避免把合法的乐观并发冲突误报为审计篡改。
- 留存报告与 API 共用相同严格语义；外部环境若存在旧链漂移必须先只读盘点和封存原始摘要，仓库不会静默重封或伪造迁移证据。

当前仓库种子不需要数据迁移，也未修改 `data/db.json`、SQLite 或 PostgreSQL。外部 SIEM/WORM、历史链基线迁移和现场签字仍是独立生产阻断项。本实现不改变 SHA-256 链对“有权重算整链的操作者”缺少独立签名防护的已知边界。
