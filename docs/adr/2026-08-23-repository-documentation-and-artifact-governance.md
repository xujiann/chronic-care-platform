# ADR：仓库文档与跟踪 PDF 采用闭集治理

- 状态：Accepted
- 日期：2026-08-23
- Owner：T00
- 影响范围：当前工作流规则、全部 Git 跟踪 Markdown、`output/pdf` 跟踪制品、治理 CI

## Problem

仓库同时保留当前规则、日期化实施快照和被后续决策替代的 ADR。旧快照中的 integration branch、
固定 baseline 等历史原文仍有证据价值，但若被当前入口引用，会让新工作树从陈旧基线创建或沿错误
方向合入。Git 还跟踪三个 PDF，其中只有一个具备现存校验器，另外两个没有可复现生成器；仅靠文件名
不能证明来源、保留理由或二进制未被手工改写。

需要一个长期、可执行的决策：区分当前规则和历史证据，完整覆盖所有跟踪 Markdown，并在不重写历史
快照或 PDF 本体的前提下锁定 PDF 的来源与完整性。

## Options

1. 维持现状，依靠维护者阅读文件名和正文判断文档权威性，PDF 只检查是否存在。
2. 移动或删除历史文档和无法重新生成的 PDF，只保留当前材料。
3. 保留现有路径，建立版本化闭集清单：Markdown 必须唯一分类为 `current`、`snapshot` 或
   `superseded`；PDF 必须登记摘要、页数、大小、引入提交、来源、保留理由和生成器可用性。

## Advantages

- 方案 1 无迁移成本。
- 方案 2 目录最简洁，并减少读者遇到旧材料的概率。
- 方案 3 不破坏审计历史；机器门禁可拒绝未分类、重复分类、历史快照改写、旧 baseline 回流和 PDF
  二进制漂移。无法证明生成器存在时会明确记录缺口，而不是伪造可再生成性。

## Disadvantages

- 方案 1 会继续产生规则冲突，且无法发现静默制品替换。
- 方案 2 删除历史证据，可能破坏既有链接和交付追溯。
- 方案 3 新增文档或 PDF 时必须同步治理清单；历史 PDF 若要更新，必须先补可复现生成源并通过独立评审。

## Migration cost

低到中。新增一个机器合同、一个只读验证器和专项测试；校准进程清单，使日常开发默认基于
`origin/main`，固定 tag 仅作为可复现证据基线。更新当前治理入口和六张地图，不移动、不删除、不
重写任何历史快照或 PDF，不涉及运行时、数据库、API、依赖或外部配置迁移。

## Risk

- 路径规则过宽可能误分类；门禁要求每个跟踪 Markdown 恰好命中一条规则，并锁定分类计数与路径摘要。
- `snapshot` 误改会破坏历史证据；门禁锁定其内容聚合摘要，修订应新增 current 文档或 superseding ADR。
- 摘要只能证明字节未漂移，不能证明 PDF 内容正确或适合生产；保留状态不构成发布或现场验收证据。
- 两个历史 PDF 缺少跟踪生成器，无法保证可再生成；在补齐生成器前保持只读，不得手工“修复”。
- 固定 evidence tag 仍有合法发布用途；不得删除该 tag 或把它重新用作默认开发/ownership 比较基线。

## Recommendation

采用方案 3。当前规则只来自 `AGENTS.md`、`ENGINEERING_GOVERNANCE.md`、机器进程清单和 Accepted
ADR；`main` 是唯一集成主干，默认开发与本地所有权验证使用最新 fetched `origin/main`，固定 baseline
tag 仅用于可复现证据。

Markdown 分类优先依据路径、日期化命名和现有 ADR 台账，不根据正文猜测业务 owner。历史 snapshot
原文不可改写；superseded 文档保留但不授予当前实施权限。`output/pdf` 的三个现存文件继续保留，禁止
手工编辑；任何合法替换必须提供受评审的生成源、更新摘要与来源证据，并通过专项门禁。回滚只回退本
治理切片，不删除文档或制品；回滚后 GOV-001、DOC-001 与 REPO-001 必须重新打开。
