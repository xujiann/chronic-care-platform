# ADR：科研合规导出职责分离与版本化命令

- 状态：Accepted
- 日期：2026-08-21
- Owner：T09（科研沙箱），T00（公共 API 与治理登记）
- 影响范围：科研数据集导出申请、独立审核、发布、审计、幂等与兼容读取

## Problem

既有 `POST /api/research/datasets/:id/compliant-exports` 在创建导出记录时同时把 `reviewStatus` 设为 `approved`、把 `exportStatus` 设为 `released`，并以同一时点补齐审核人与水印。申请者不经过独立审核即可得到“已发布”状态，最小必要字段、发布证据、职责分离、并发覆盖和命令重放均无法被可靠证明。

同时，现有 `compliantDataExports` 中已有可读的历史 released 记录；本切片不得直接编辑数据文件、创建平行核心概念或把科研沙箱拆成独立服务。必须在保持集合、创建路径和历史读取兼容的前提下建立失败关闭的生产闭环。

## Options

1. 维持现状，仅在页面提示导出仍需人工审批。
2. 在现有科研边界内建立版本化工作流：创建只产生 pending/blocked 申请；新增监管 action API 执行 approve、reject、release；引入职责分离、CAS、幂等回执和追加式决策历史；历史 released 记录保持只读兼容。
3. 新建独立导出审批服务和新事实源，一次迁移全部历史记录及调用方。

## Advantages

- 方案 1：实现成本最低，没有接口行为迁移。
- 方案 2：申请、审核、发布形成可测试状态机；未审核数据默认阻断；机构只能看到自己申请的记录；命令具备稳定冲突语义；无需修改核心表、数据文件或部署拓扑。
- 方案 3：长期可获得独立伸缩、独立部署和更强物理隔离。

## Disadvantages

- 方案 1：安全缺口继续存在，页面提示不能代替服务端授权和状态约束。
- 方案 2：调用方需要处理 pending、approved-pending-release、released 和 rejected；监管审核与发布证据仍需由真实制度、人员和外部系统提供；现阶段仍复用模块化单体存储。
- 方案 3：迁移范围大，需要新存储、服务身份、消息一致性、双读切换、回滚和运维体系；在尚无独立流量及团队证据时会提前增加分布式复杂度。

## Migration cost

方案 2 为中等成本：保留 `compliantDataExports` 和既有创建路径；新增 `research-compliant-export-workflow.v1` 与 `POST /api/research/compliant-exports/:id/actions`；新记录从 `domainVersion=1` 开始。既有无版本 released 记录按版本 0 兼容读取，不回写、不伪造历史决策链，也不批量迁移。调用方应先适配新状态，再由现场流程接入真实审核与发布证据。

方案 3 为高到极高成本，包含数据迁移、跨服务一致性、部署、监控和现场切换，不在本阶段实施。

## Risk

- 兼容风险：旧客户端若把创建成功等同于可下载，会看到 pending/blocked；通过保留 201 和记录基本形状、明确新增状态来控制。
- 安全风险：审核或发布主体与申请主体相同、直接标识符进入字段清单、机构跨范围读取；服务端均失败关闭。
- 并发风险：陈旧版本覆盖已审核结果；由 `expectedVersion` CAS 返回稳定 409。
- 重放风险：同一命令键携带不同载荷；由摘要比对返回稳定 409，同载荷重放不重复决策和审计。
- 证据风险：代码中的 evidence reference 不是现场证据本身；没有真实审批、对象存储、脱敏验证和接收方签收时不得宣称生产就绪。
- 回滚风险：回滚 action 路由不会自动改变已产生的 pending 记录；这些记录保持阻断是安全默认，不应降级为自动发布。

## Recommendation

采用方案 2。创建接口只登记申请，不再隐式审批和发布；监管角色使用版本化 action 命令独立批准或退回，只有已批准记录在补齐发布证据和水印后才能进入 released。监管审核/发布者不得是申请者；机构列表只返回本机构主体发起的记录；所有状态变化追加 decision history，并以 command ID 和载荷摘要保证幂等。

非目标包括：生成真实导出文件、替代真实伦理/数据使用审批、修改 SQLite schema、迁移历史记录、引入新服务或宣称现场生产就绪。未来只有在独立流量、团队、数据主权和运维证据同时满足已接受的服务提取标准后，才重新评估方案 3。
