# ADR：人工智能治理与临床决策支持边界

- 状态：Accepted
- 日期：2026-09-05
- 授权：用户批准下一步开发计划并要求实施；本记录落实该方向的首个兼容增量。
- Owner：T01 治理策略，T06 临床规则与提醒事实，T00 跨域装配。

## Problem

现有临床辅助已有规则、提醒、医生回执和工作站页面，但缺少规则版本审批、独立复核和受控回滚。遗留访问逻辑在机构信息缺失时扩大访问范围；回执和配置写入尚未完整保护重放、并发与审计失败。新增 AI 能力必须复用这些事实，并明确仓库治理审批与生产授权的区别。

## Options

1. 新建独立 AI 平台、模型库和临床数据副本。
2. 在现有混合路由继续堆叠审批与临床逻辑。
3. T01 提供版本化治理策略，T06 提供临床领域端口，T00 保留兼容接口并装配既有持久化和审计。

## Advantages

采用方案 3。`ai-governance.v1` 只管理规则卡、来源与评测引用、版本、独立审批、暂停和回滚；`clinical-decision-support.v1` 管理范围裁剪及医生回执。复用 `phase2ClinicalAssistRules`、`phase2ClinicalAssistAlerts`、`phase2ClinicalAssistReceipts`，不创建居民、机构、病历、模型推理服务或第二规则事实源。治理策略由 T01 实现，但临床集合 Owner 保持 T06，写入通过明确临床聚合边界完成。

## Disadvantages

首个增量只支持既有规则的治理，模型在线推理、漂移自动采集、医院电子签名及外部正式验证仍未实现。共享运行时与遗留 JSON/SQLite 兼容持久化不能证明多实例 exactly-once 或生产可用。

## Migration cost

治理元数据作为既有规则内的可选版本化字段，未登记规则按版本 0 解释；只在显式命令中写入，不启动时回填，不改变 SQLite v17 的表结构。新治理写入口必须有 expectedVersion 和 idempotencyKey。旧临床回执 payload 保持兼容，可选启用版本和幂等保护，未提供时不得宣称严格幂等。已进入治理的规则禁止通过旧配置入口绕过治理，返回稳定冲突码。未来生产迁移必须沿用既有迁移、核对和回滚要求。代码回滚保留新增字段；已治理数据不能由旧版本未经审查重新放开写入。

## Risk

防止规则内容改变后继承旧审批、同一人员登记后自审、缺机构身份扩大范围、请求重放、并发覆盖以及审计失败后的部分写入。治理字段和引用采用白名单，不保存患者原文、密钥或 provider 原始消息。可信身份只来自服务端会话与目录。变更在独立副本上构造，审计成功后单次持久化；审计或存储失败不得污染读到的共享状态。规则登记、审批、暂停和回滚均不触发自动诊断、处方或医嘱。

## Recommendation

兼容状态接口不再返回四个原始临床辅助集合，全量 state 保存必须省略或保持原值，集合级保存拒绝这四项；专用接口提供经过范围裁剪的公共投影。旧 config 仅保留非生产环境主管部门兼容，生产拒绝并指向有增强认证的治理入口。并发锁只包围读校验和提交，不等待请求体、不拦截未命中路由。医生端提交实际保留理由，并携带当前版本及稳定幂等键；网络重试不另造业务回执。

先实现规则登记—送审—独立批准/退回—暂停—回滚到待审的闭环，再把临床读取和医生回执收敛到小型端口。来源摘要只表示受控记录绑定，不代表外部验证通过。所有新增视图和命令固定 `productionReady=false`，生产 NO-GO；上线仍需真实机构接入、签名证据、数据库演练、独立验收与正式授权。
