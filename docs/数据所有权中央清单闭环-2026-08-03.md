# 数据所有权中央清单闭环

## 结论

`config/domain-data-ownership.json` 是业务集合所有权的唯一中央清单。本次将平台治理写契约涉及、但此前未登记的 44 个业务集合补入清单，并登记 T06 幂等命令必需的 `emergencySignalCommandInbox`，共新增 45 个业务集合。清单版本由 `1.0.0` 升至 `1.1.0`。

所有者依据领域事实来源和进程职责确定，不以平台治理路由代写行为作为所有权证明：

- 平台治理：发布控制、数字医院治理、商用密码治理、运行事件和治理命令回执。
- 公共卫生：公卫协同、疾病报告队列及其回执。
- 临床专科：临床辅助、质量整改、检查检验互认记录及引用。
- 服务协同：资源调度、家庭医生业务和跨领域任务消息。
- 医保支付：药品耗材监管业务。

平台治理需要编排其他领域数据时，只登记为 reader；不会因为平台路由参与写入而取得业务所有权。

`emergencySignalCommandInbox` 由临床专科拥有，用于持久化急救信号命令幂等回执，默认不授权任何跨领域 reader。

## 专用系统集合

以下集合继续使用专用系统策略，不重复登记为业务集合：

- `dataAccessLogs`
- `platformProcessAudit`
- `securityEvents`

架构测试会同时验证专用系统策略和业务中央清单，并阻止写契约新增未登记集合、同一集合声明冲突所有者，或把系统集合重复登记为业务所有权。

## 边界

本次只闭合中央声明和架构门禁，不改变 T02 路由、不迁移数据，也不放宽任何领域的 Repository 写权限。现有跨领域代写仍应继续迁移到版本化契约、领域 Repository、Unit of Work 和 outbox/inbox。
